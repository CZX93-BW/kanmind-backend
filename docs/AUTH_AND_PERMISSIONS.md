## Authentication and Authorization

Authentication answers:

> Which user is making this request?

Authorization answers:

> May that user perform this operation on this resource?

KanMind uses DRF token authentication to identify API users.

Permissions, queryset filters and relationship validation then determine
what those users may access or change.

A valid token does not grant access to every board, task or comment.

## Registration

`POST /api/registration/` is public.

The registration serializer accepts:

- `fullname`
- `email`
- `password`
- `repeated_password`

It validates the email address, checks uniqueness after domain normalization,
compares both passwords and invokes Django's configured password validators.

The user manager stores the password through `set_password()`.
The password confirmation is removed before account creation and is not stored.

Registration creates the user and token inside a database transaction.

The successful HTTP 201 response contains:

```json
{
  "token": "<generated-token>",
  "fullname": "Example User",
  "email": "example@example.com",
  "user_id": 1
}
```

The token and ID in actual responses are generated by the backend.

Regular registration does not expose staff or superuser flags.
The user manager defaults both flags to `False`.

## Login

`POST /api/login/` is public.

The login serializer validates the submitted email and password, then calls
Django's `authenticate()` function.

The successful HTTP 200 response contains the same keys as registration.

The login view uses `Token.objects.get_or_create()`. Logging in again can
therefore return the existing token; login does not automatically rotate it.

Wrong credentials and inactive accounts are rejected with the same
application-level validation message:

```json
{
  "non_field_errors": [
    "Invalid email or password."
  ]
}
```

This login failure returns HTTP 400. It is distinct from HTTP 401 responses
on protected endpoints with missing or invalid token authentication.

Registration and login explicitly use `AllowAny` and an empty
`authentication_classes` list. They do not require an existing token.

## Authenticated Requests

Protected requests use this header:

```http
Authorization: Token <returned-token>
```

The prefix is `Token`, not `Bearer`.

The project configures these defaults in `core/settings.py`:

- `TokenAuthentication`
- `IsAuthenticated`

A protected API request requires its token even if the same browser is logged
in to Django Admin. The API does not use the admin session as its configured
authentication mechanism.

The project does not implement a logout, token refresh or token revocation
API endpoint. Removing a token from a client does not delete the server-side
token.

Tokens are credentials. Do not commit them, include them in public screenshots
or save live tokens in exported Postman examples.

## Roles and Relationships

The API's roles are relationships to particular objects, not global account
categories.

| Role | Meaning |
| --- | --- |
| Board owner | The user referenced by `Board.owner` |
| Board member | A user included in `Board.members` |
| Task creator | The user referenced by `Task.created_by` |
| Assignee | The user referenced by `Task.assignee` |
| Reviewer | The user referenced by `Task.reviewer` |
| Comment author | The user referenced by `Comment.author` |

A user can hold several roles simultaneously.

For example, the board owner can also be a member, task creator and reviewer.
Each operation checks the relationships relevant to that operation.

An outsider in a test means a user without the relationships required for
the tested action.

## Permission Matrix

Except for registration and login, every operation requires authentication.

| Operation | Additional access condition |
| --- | --- |
| Register | Public |
| Log in | Public |
| Look up a user by email | No additional board relationship required |
| Create a board | No additional relationship required |
| List boards | Results contain boards owned by or shared with the user |
| Retrieve a board | Board owner or member |
| Update a board | Board owner or member |
| Delete a board | Board owner |
| Create a task | Member of the target board |
| Update a task | Member of the task's board |
| Delete a task | Task creator or board owner |
| List assigned tasks | Results match `assignee=request.user` |
| List reviewing tasks | Results match `reviewer=request.user` |
| List task comments | Member of the task's board |
| Create a comment | Member of the task's board |
| Delete a comment | Comment author, through the matching task URL |

There is no automatic API permission override for `is_staff` or
`is_superuser` in the custom permission classes.

## Board Access

### Ownership is separate from membership

Creating a board assigns the requesting user as its owner.
It does not automatically add that user to `members`.

An owner without membership can:

- See the board in their board list
- Retrieve its details, including nested tasks
- Update its title and membership
- Delete the board
- Delete tasks belonging to the board

That ownership alone does not permit task creation, task updates,
comment listing or comment creation.

The owner can add themselves as a member when participation is needed.

### Members can manage membership

Board updates are allowed for both owners and members.

A member can therefore replace the board membership list, including removing
themselves or another member.

Removing a user does not change board ownership.

Subsequent requests use the resulting membership. A removed user loses
member-based access unless another applicable relationship grants access.

### Board listing

List access is implemented through queryset filtering.

An authenticated user with no accessible boards receives HTTP 200 and an
empty list:

```json
[]
```

The list does not return HTTP 403 merely because the user has no boards.

## Task Access

### Creation and updates

Task creation requires membership of the submitted board.

Because a new task does not exist yet, the creation check takes place in
`TaskWriteSerializer.validate_board()`.

Updating an existing task checks `IsTaskBoardMember` during object lookup.

The serializer additionally validates assignee and reviewer membership.
It also rejects attempts to move the task to a different board.

Retained assignments are revalidated during partial updates.
An assignment to a former member can therefore block an unrelated update
until it is cleared, replaced or the user's membership is restored.

### Deletion

Task deletion uses `IsTaskCreatorOrBoardOwner`.

Being an assignee, reviewer or ordinary member does not independently grant
the right to delete a task.

The deletion permission does not additionally require current membership.
A task creator who has left the board still satisfies the creator condition.
A board owner without membership still satisfies the owner condition.

### Personal task lists

The personal lists filter directly by the authenticated user:

- `assigned-to-me` matches the assignee.
- `reviewing` matches the reviewer.

They do not apply an additional current-board-membership filter.

If an assignment remains after membership removal, that assignment can still
appear in the corresponding personal list. It does not restore permission
to update the task.

## Comment Access

### Listing and creation

`CommentListCreateView` retrieves the parent task and explicitly calls
`check_object_permissions()` for that task.

The user must belong to its board.

During creation, the view supplies:

```python
serializer.save(task=task, author=request.user)
```

The task comes from the URL, and the author comes from authentication.

### Deletion

`IsCommentAuthor` allows only the comment author to delete a comment.

Board ownership and task creation do not independently grant permission
to delete another user's comment.

The deletion permission does not additionally require board membership.
An author who has left the board can still delete their own comment through
its matching task URL.

Before checking authorship, the view restricts lookup to comments belonging
to the task specified in the URL.

A real comment requested through a different task returns HTTP 404.

## Validation and Lookup Order

For a protected request that matches an API route, the relevant sequence is:

1. Authenticate the request.
2. Check request-level permissions.
3. Perform action-specific lookup and validation.
4. Check object permissions when retrieving an existing object.
5. Validate and save input where applicable.
6. Build the response.

The precise lookup and serializer sequence depends on the operation.

| Scenario | Result |
| --- | --- |
| Missing token on a protected route | HTTP 401 |
| Invalid token on a protected route | HTTP 401 |
| Existing object but insufficient permission | HTTP 403 |
| Missing object during lookup | HTTP 404 |
| Comment requested through another task | HTTP 404 |
| Invalid fields after access checks | HTTP 400 |

Task detail and comment deletion views explicitly validate string-based
URL IDs.

For these matched routes, missing authentication is rejected before their
custom ID validation.

Other routes use integer URL converters. If a malformed path does not match
a route, Django can return HTTP 404 before DRF authentication runs.

A status code must therefore be interpreted in the context of the requested
route and operation.

## Django Admin

Django Admin uses session authentication and its own administration rules.

The custom user model supports email-based admin login.

Staff status and Django model permissions control administration access.
Superuser behavior in Admin does not create a bypass in the custom API
permission classes.

Admin edits do not automatically execute API serializers or API permissions.
Administrative maintenance must respect the application's relationships
and validation rules.

## Configuration and Boundaries

### Trusted values

The backend determines these values during API creation:

| Value | Source |
| --- | --- |
| Board owner | Authenticated user |
| Task creator | Authenticated user |
| Comment author | Authenticated user |
| Comment task | Task resolved from the URL |

Clients supply editable data, not these ownership decisions.

### CORS

CORS allows the configured frontend origin to read API responses in a browser.

It does not identify users or grant object access. A request still needs a
valid token and must pass the applicable permissions.

Postman does not enforce browser CORS rules, so CORS requires separate
browser verification.

### Local configuration

The Django secret key is loaded from the environment.
`.env` and the SQLite database are excluded from Git.

The current setup is intended for local development and assessment.
The project does not claim to provide a production security configuration.
